KmerSutra v0.40 handover notes for public dataset benchmark chat
==============================================================

Date: 2026-06-03

Context
-------
The v0.34 Plasmodium/outgroup database build produced clean specificity but poor
LOD values in the comparable raw-read spike-in benchmark. The current sensitive
threshold setting was:

    MIN_UNIQUE_KMERS=10
    MIN_POSITIVE_SEQUENCES=2
    MIN_K_VALUES_POSITIVE=1
    MIN_EXACT_HITS=10
    MIN_BEST_K=101
    MIN_CONFIDENCE_SCORE=0.50
    MAX_CONFLICT_RATIO=0.10

This retained tracked-target specificity of 1.0 and clean shuffled negatives,
but LOD50/LOD100 values remained too high for a practically useful raw-read
detector. Same-genus Plasmodium near-neighbour signal was considered acceptable
if reported transparently, but the high LOD values were not acceptable.

v0.39 threshold sweep conclusion
--------------------------------
KmerSutra v0.39 added a threshold sweep. The sweep showed that further
threshold relaxation, including u8/p1/e8 and u5/p1/e5, gave only modest
improvements. It did not recover the older v0.30-style LOD values. Therefore,
the problem is unlikely to be solved by threshold relaxation alone.

Diagnosis
---------
The v0.34 panel was heavily dominated by k=151 records. Because the
candidate-universe sampler processed k values long-to-short, long k=151 markers
claimed many bin/cross-k opportunities before shorter k values could be
retained. This is highly specific but poorly matched to noisy raw ONT reads.

v0.40 package update
--------------------
KmerSutra v0.40 adds a raw-ONT balanced build profile:

    --marker_profile raw_ont_balanced
    --candidate_k_order auto

Under this profile, candidate-universe sampling uses short_to_long order, so
k=51, k=77 and k=101 markers are sampled before k=151 markers during
cross-k de-correlation. The aim is to produce a more raw-read-sensitive panel
without relaxing conflict ratio or confidence-score reporting controls.

Recommended next Plasmodium database build
------------------------------------------
Use the included script:

    run_kmersutra_build_global_candidate_v040_raw_ont_balanced_tmpdir.sh

Key expected paths/settings:

    DB_ROOT=/home/pthorpe001/data/databases/kmersutra_db
    SOURCE_CONFIG=/home/pthorpe001/data/databases/kmersutra_db/ncbi_genomes_plasmodium_outgroups_v4/kmersutra_genome_config.tsv
    K_VALUES="51 77 101 151"
    MARKER_PROFILE=raw_ont_balanced
    CANDIDATE_K_ORDER=auto
    GLOBAL_SOURCE_INDEX_MODE=candidate_universe
    MARKER_SELECTION=independent_multik_genome_spread
    ASSEMBLY_AWARE_BINNING=true
    WRITE_MODULE_PARQUET=true

After the build, inspect panel composition before screening:

    zcat species_kmer_panel.tsv.gz | cut -f2 | sort | uniq -c

The v0.40 build should not be dominated by k=151 to the same extent as v0.34.
If it remains dominated by k=151, further build-level per-k quotas will be
needed.

Public dataset implications
---------------------------
Do not rely on the v0.34 panel as final for public raw ONT benchmarks if the
question is practical sensitivity. The public dataset benchmark chat should note
that v0.34 was too long-k heavy and that v0.40 is intended to produce a more
raw-read-balanced panel.

Recommended benchmarking plan:

1. Complete/record the public dataset benchmark currently running, but label it
   clearly with the panel version and thresholds used.
2. Build the v0.40 raw-ONT balanced panel.
3. Re-run the comparable Plasmodium spike-in screen first.
4. Only if v0.40 improves LOD materially while preserving clean negatives, use
   the v0.40 panel for the public dataset benchmark.

Repository hygiene
------------------
This is a package update, not an ad hoc script. It includes tests and release
notes. Temporary scripts should remain outside the GitHub-managed package tree.
