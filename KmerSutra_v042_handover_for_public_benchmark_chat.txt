KmerSutra v0.42 handover notes for public benchmark chat
========================================================

Purpose
-------

These notes explain why v0.42 was built and how it should be used in the public
bacterial / Zymo D6300 benchmark and the Plasmodium benchmark work.

Short version
-------------

Pause all v0.40/v0.41-derived screening as final benchmark evidence. v0.40 and
v0.41 were useful diagnostics but not final build designs. v0.42 should be used
for the next database build because it combines:

    per-k per-bin quotas
    plus
    interval-aware cross-k locus separation

This is intended to produce a balanced multi-k panel without letting different
k values be sampled as nested markers from the same local locus.

Problem sequence
----------------

1. v0.34 / earlier global candidate builds were too k=151-heavy.

   For the Plasmodium v0.34 build, the final panel was dominated by k=151. This
   gave excellent specificity but poor raw ONT sensitivity and weak LOD values.
   Threshold sweeps showed that relaxing detection thresholds alone did not fix
   the LOD problem. The bottleneck was likely marker composition / build policy.

2. v0.40 raw_ont_balanced over-corrected.

   v0.40 changed candidate sampling to short-to-long so that lower-k markers
   could be retained before k=151. This helped avoid k=151 dominance, but the
   same global cross-k position blocker was still active. Because k=51 was now
   processed first, k=51 claimed local regions and blocked later k=77/k=101/k=151
   markers.

   In the public bacterial benchmark, this produced a very poor multi-k ladder.
   Example expected species retained markers:

       Escherichia coli:          k51=1,349; k77=20; no k101/k151
       Listeria monocytogenes:    k51=2,619 only
       Pseudomonas aeruginosa:    k51=2,681; k77=20
       Bacillus subtilis:         k51=4,189; k77=10
       Staphylococcus aureus:     k51=2,729; k77=30; k101=10; k151=10
       Salmonella enterica:       k51=4,715; k77=40; k101=4; k151=20

   Conclusion: v0.40 should not be used as the final public benchmark database.

3. v0.41 fixed k starvation but allowed nested loci.

   v0.41 added per-k per-bin quotas, for example:

       k=51:  3 per bin
       k=77:  3 per bin
       k=101: 2 per bin
       k=151: 2 per bin

   This prevents k=51 from consuming the quota reserved for longer k values.
   However, to avoid reintroducing starvation, v0.41 set cross-k spacing to zero.
   That can allow nested k-mers from the same local sequence region, such as a
   51-mer contained inside a 77-mer, to be retained as multi-k evidence.

   This is not ideal because multi-k evidence from one locus is not independent
   genome-wide evidence.

4. v0.42 is the current fix.

   v0.42 adds:

       --marker_profile raw_ont_multik_locus_balanced

   Defaults:

       --candidate_k_order auto
       --max_per_genome_bin_by_k 51:3,77:3,101:2,151:2
       --min_cross_k_marker_distance 250

   The cross-k distance is now interval-aware, not just start-position based.
   It rejects overlapping, contained, nested or nearby intervals from different
   k values on the same contig.

Conceptual goal
---------------

The final panel should behave like a taxonomic fingerprint:

    k=51 and k=77 provide raw-read sensitivity
    k=101 and k=151 provide more specific anchor evidence
    k values should be represented across different loci
    one k value should not starve the others
    nested k-mers from the same locus should not be counted as independent
        multi-locus support

Recommended next public benchmark workflow
------------------------------------------

1. Stop any current v0.41 database build if it is still running.
2. Install or pull v0.42.
3. Build the database using:

       qsub run_kmersutra_build_global_candidate_v042_raw_ont_multik_locus_balanced_tmpdir.sh

   or equivalent settings:

       --marker_profile raw_ont_multik_locus_balanced
       --candidate_k_order auto
       --max_per_genome_bin_by_k 51:3,77:3,101:2,151:2
       --min_cross_k_marker_distance 250
       --k_values 51 77 101 151

4. Do not screen immediately after the build finishes.
5. First inspect the per-species k profile.

Suggested command:

       BUILD_DIR="/path/to/v042/build"

       zcat "${BUILD_DIR}/species_kmer_panel.tsv.gz" \
         | awk -F '\t' '
           NR == 1 {
             for (i = 1; i <= NF; i++) {
               if ($i == "species_name") species = i
               if ($i == "k") kval = i
             }
             next
           }
           {
             count[$species "\t" $kval]++
           }
           END {
             for (key in count) print key "\t" count[key]
           }' \
         | sort -k1,1 -k2,2n

6. Expected outcome is not equal k counts. Instead, expected species should have
   meaningful representation at k=51, k=77, k=101 and k=151.

7. If k=101/k=151 remain tiny or absent, do not proceed to full screening. The
   build policy still needs work.

8. If the k ladder looks sensible, run the comparable spike-in benchmark first.

Important benchmark interpretation
----------------------------------

Expected species / expected targets are benchmark metadata only. They should be
used to calculate TP, FP, FN, LOD, sensitivity and specificity for known
benchmark samples. They should not be required for real unknown-sample
screening.

Real screening should be query-agnostic:

    screen across candidate taxa
    report the most specific supported taxonomic level
    use LCA / rank-aware interpretation when species-level evidence is ambiguous
    report background/conflict evidence transparently

Do not design the real pipeline around knowing the expected species in advance.

Repository hygiene
------------------

Future shell wrappers should use:

    /home/${USER}/...

rather than hard-coded usernames.

Old shell wrappers should be removed from release packages to avoid confusion.
The v0.42 release only includes the current recommended build wrapper:

    run_kmersutra_build_global_candidate_v042_raw_ont_multik_locus_balanced_tmpdir.sh
