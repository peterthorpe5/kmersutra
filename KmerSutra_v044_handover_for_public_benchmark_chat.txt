KmerSutra v0.44 handover for public benchmark chat
==================================================

Context
-------
In the Plasmodium comparable benchmark, the locus-balanced multi-k database
restored useful LOD50 values, but the three-genome Plasmodium vivax LOD100
remained high. A threshold sweep showed that simply relaxing the reporting
thresholds did not improve the limiting case. The issue therefore appeared to
be upstream: exact long-k matching was too brittle for noisy raw-read input.

KmerSutra v0.43 added a raw_ont_sensitive screen/call mode:

  --screen_preset raw_ont_sensitive
  --call_preset raw_ont_sensitive

This allowed one mismatch for long k-mers, defaulting to:

  max_mismatches = 1
  fuzzy_min_k = 101

and changed calling so exact + fuzzy evidence could pass a total support floor.

Problem found after v0.43
------------------------
The fuzzy mode worked conceptually, but the log message:

  Screening records using N worker(s), chunk_size=10000, max_mismatches=1
  Using canonical/fuzzy screening path because max_mismatches=1

raised concern that the mode would be too slow for large FASTQ/public benchmark
runs. The original fuzzy implementation generated all one-mismatch neighbours
for every query k-mer window, which is approximately 3*k candidates per window.
For k=101/151 and large raw-read FASTQ files, that is a substantial CPU burden.

v0.44 change
------------
v0.44 keeps the same user-facing command and presets, but replaces the
one-mismatch search strategy with a half-seed candidate index.

For each panel k-mer, the code indexes two exact seeds:

  left half
  right half

A true one-substitution match must share at least one exact half seed with the
panel k-mer. Therefore each query k-mer only has to check candidate panel k-mers
that share a half seed, and then verify those by Hamming distance. This avoids
constructing all 3*k mutated query neighbours.

Expected result
---------------
The biological behaviour should be the same as v0.43 for one-mismatch long-k
rescue, but runtime should be materially better. This is especially relevant to
the public Zymo/raw-ONT benchmark where single FASTQ screening was already slow.

Command compatibility
---------------------
The same benchmark command can be used. No shell-level change is needed if the
wrapper already passes:

  SCREEN_PRESET=raw_ont_sensitive
  CALL_PRESET=raw_ont_sensitive

and leaves these empty to use preset defaults:

  MAX_MISMATCHES=""
  FUZZY_MIN_K=""
  MIN_TOTAL_HITS=""

The log should now say something like:

  Using accelerated one-mismatch seed-index fuzzy path for k >= 101 with ... seed keys

instead of the older generic canonical/fuzzy warning.

Plasmodium next step
--------------------
Install v0.44 and rerun the same v0.43 raw_ont_sensitive fuzzy-long-k screen
against the existing locus-balanced Plasmodium panel. Do not rebuild the
Plasmodium database for this test. The aim is to test whether one-mismatch
long-k evidence reduces the hard three-genome P. vivax LOD100 while keeping:

  - shuffled negatives clean;
  - off-target summary empty or near-empty;
  - specificity/precision at or close to 1.0.

Public benchmark next step
--------------------------
Install v0.44 before continuing the public dataset benchmark. If the public run
was started under v0.43 and is very slow, consider stopping and restarting under
v0.44 so the accelerated one-mismatch seed path is used.
