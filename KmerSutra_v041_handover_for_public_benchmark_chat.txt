KmerSutra v0.41.0 handover for public benchmark chat
====================================================

Context
-------

This handover is for the public bacterial/Zymo D6300 benchmark chat and the
parallel Plasmodium benchmark chat.

The public bacterial v0.40 raw_ont_balanced database showed a serious k-profile
problem. Expected species retained mostly k=51 markers, with very weak or absent
k=101/k=151 support:

    Escherichia coli:        k51=1,349; k77=20; no k101/k151
    Listeria monocytogenes:  k51=2,619 only
    Pseudomonas aeruginosa:  k51=2,681; k77=20
    Bacillus subtilis:       k51=4,189; k77=10
    Staphylococcus aureus:   k51=2,729; k77=30; k101=10; k151=10
    Salmonella enterica:     k51=4,715; k77=40; k101=4; k151=20

This is not a balanced multi-k diagnostic panel and should not be used as the
final benchmark database.

Interpretation of the problem
-----------------------------

v0.40 changed candidate sampling to short_to_long for raw ONT sensitivity. That
helped lower-k retention, but it over-corrected because the candidate-universe
sampler still applied the global cross-k marker exclusion distance. Since k=51
was sampled first, it could block most later k=77/k=101/k=151 markers from the
same local genomic regions.

The issue is therefore not simply a threshold problem. It is a database-build
logic problem: the candidate sampler needs to preserve a multi-k ladder rather
than allowing either long k values or short k values to dominate.

v0.41.0 package update
----------------------

v0.41.0 adds a new profile:

    --marker_profile raw_ont_multik_balanced

and a new CLI option:

    --max_per_genome_bin_by_k "51:3,77:3,101:2,151:2"

The new profile defaults are:

    candidate_k_order=input
    max_per_genome_bin_by_k=51:3,77:3,101:2,151:2
    min_cross_k_marker_distance=0

Why min_cross_k_marker_distance defaults to 0 for this profile
--------------------------------------------------------------

The per-k quotas now control local evidence density. Keeping a global cross-k
block of 5000 bp would reintroduce starvation between k values. For raw ONT
multi-k panels, the aim is to keep a usable ladder of k=51, k=77, k=101 and
k=151 markers. The build can still be made more stringent later if the final
panel contains too much local redundancy.

Installed/package tests
-----------------------

Use unittest, not nose2, unless explicitly requested.

The v0.41 test run used:

    python -m unittest discover -s tests -p 'test*.py'

Result:

    Ran 328 tests in 12.628s
    OK

New tests verify that short k values cannot starve longer k values in a simple
candidate-universe sampling example.

Recommended action for the public benchmark chat
------------------------------------------------

1. Pause screening with the v0.40 database:

       kmersutra_zymo_d6300_species_reference_v040_raw_ont_balanced_k51_77_101_151_20260603_141938

   Treat this database as diagnostic only.

2. Install/pull v0.41.0.

3. Rebuild the bacterial/Zymo database using:

       --marker_profile raw_ont_multik_balanced
       --candidate_k_order auto
       --max_per_genome_bin_by_k "51:3,77:3,101:2,151:2"
       --min_cross_k_marker_distance 0

   If the wrapper script is adapted from v0.40, ensure the output folder name is
   labelled v041 and rawontmultikbalanced.

4. Before screening, inspect final panel k composition by species:

       BUILD_DIR="/path/to/v041/build"
       zcat "${BUILD_DIR}/species_kmer_panel.tsv.gz" \
         | awk -F '\t' 'NR == 1 {for (i=1; i<=NF; i++) {if ($i=="species_name") s=i; if ($i=="k") k=i}; next} {count[$s"\t"$k]++} END {for (key in count) print key"\t"count[key]}' \
         | sort -k1,1 -k2,2n

5. Do not proceed to full screening unless k=101 and k=151 have non-trivial
   retention for expected species.

Recommended action for the Plasmodium chat
------------------------------------------

The same logic applies to the Plasmodium benchmark. v0.34 was too k=151-heavy
and insensitive; v0.40 risks becoming too k=51-heavy. v0.41 is intended to
preserve a usable multi-k ladder.

Build the next Plasmodium database using:

    run_kmersutra_build_global_candidate_v041_raw_ont_multik_balanced_tmpdir.sh

Then inspect:

    species_kmer_panel.tsv.gz
    kmer_collection_summary.tsv
    candidate_sampling_audit.tsv
    candidate_evidence_audit.tsv
    target_evidence_build_summary.tsv
    metrics/panel_evidence_rank_summary.tsv

The goal is not equal counts at every k. The goal is non-trivial representation
of k=77, k=101 and k=151 while retaining enough k=51 for raw-read sensitivity.

Suggested stopping rule before screening
----------------------------------------

Proceed to screening only if:

    expected species retain meaningful k=51/k=77/k=101/k=151 markers
    k=51 does not dominate to the exclusion of longer k values
    k=151 does not dominate to the exclusion of shorter k values
    build metrics and RAM/runtime look acceptable

If k=101/k=151 are still too sparse, the next possible profile would increase
longer-k quotas, for example:

    51:3,77:3,101:3,151:2

or:

    51:3,77:3,101:2,151:3

Do not benchmark a poorly balanced database just because it completed.

Repository hygiene
------------------

This is a package-level update, not an ad hoc script. Temporary analysis scripts
should not be copied into the GitHub-managed KmerSutra repository. Only tested
package code, release notes, wrapper scripts and reproducibility documents should
be committed.
